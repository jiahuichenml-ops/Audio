# git-signoff：拍板式存档协议

AI 执行 Git，用户测试并拍板。根据自然语言台词匹配动作，不要求用户在提示词里重复指定技能名。沿用本次会话已经明确的范围和授权，不要求用户重复确认。

## 先判断阶段与授权

- **编码结束**：报告改动、待测项目和预期结果，等待用户测试；不把代码写完称为验收通过，不自动 commit 或 merge。
- **用户只说测试通过**：记录测试对象和范围，建议下一步存档；测试事实本身不是 Git 操作授权。
- **用户明确动作与对象**：先简短汇报当前分支、本次文件、工作区和暂存区状态、将执行的动作，然后执行。上下文已明确的内容不用再问；缺少范围、目标或发生冲突时，只确认缺项。
- “后端上传接口测试通过，存档”已授权为这批后端改动建立 commit，不需要再次拍板；回报“后端独立测试通过，前端尚未联调”，不能称全链路完成。
- “打存档点：名称”是为本轮明确范围建立 commit 的授权，不是创建 tag。沿用上下文已有的测试范围，不重新追问；未验证的部分据实写为待测，不要求先把所有功能验收完才允许保存进度。
- 复制请求中的 `【填写测试结果】`、`【项目路径】` 等未填占位符不是实际事实或目标。不能据此声称验收通过或执行合并；先从会话和只读检查补齐，实际项目目标仍不明确才补问。用户明确要求保存未完成进度时，可按确定范围建立“待测／未完成”存档。
- 授权只覆盖指定动作：允许编码不等于允许 Git；commit 不包含 push，push 不包含 merge；“推送 PR”包含推送功能分支和创建 PR，不包含补做 commit 或合并。只读检查可直接进行。

## 台词与动作

| 用户台词 | AI 执行动作 |
| --- | --- |
| “骨架测试通过，在 main 存档” | 确认项目与仓库边界、main 和实际测试结果，再检查并提交本次骨架。目标不属于任何现有仓库且用户已明确该项目时，可先 `git init -b main`；已有仓库仅在项目边界已确认时沿用，不随意改名分支。 |
| “创建feat/voice-metting分支，后续接口会在该分支上开发” | 从用户指定或上下文明确的已验收起点创建并切换本地分支；按用户给出的拼法使用 `feat/voice-metting`，默认不 push。若同名分支已存在，先核对而不是重建。 |
| “打存档点：骨架构建”／“存档”／“commit”／“提交” | 检查本轮差异和暂存区，只 add 本次确切路径，再检查并 commit；使用给出的存档名称说明本轮变化，不创建 tag、不 push。 |
| “推上去”／“push” | 将已存在且属于本次授权范围的提交推到确认的远端与分支；不 add、不补做 commit。 |
| “存档推上去” | 先执行本次 commit，再推送授权提交；报告两步各自的结果。 |
| “推送 feat/voice-metting 分支并创建 PR 到 main”／“推送 PR” | 沿用已明确的仓库、源分支和目标分支，推送已有授权提交，检查并创建或复用对应 PR；不额外 commit、不自动合并。缺少的目标从上下文和只读检查确定，仍不明确才补问。 |
| “连接这个 GitHub 仓库：实际地址” | 检查现有 remote 和用户给出的真实地址；按授权配置对应 remote。连接不包含提交或推送。 |
| “把 feat/voice-metting 合进 main，整链测试通过，合了” | 检查源、目标及覆盖本次改动的测试事实，汇报后按已明确方式合并；不机械再问同一问题。若授权的是本地合并，合并后由用户复测主线，确认通过且已有 push 授权才推主线。 |

“合了”可以沿用已明确的源、目标和测试事实；缺其中任何一项才补问。“保存到 GitHub”等台词若上下文不能区分 commit 与 push，先说明拟执行范围再请用户补充。

## 存档前检查

1. 在实际项目目录运行 `git rev-parse --show-toplevel` 核对仓库根。如果返回项目的父目录，先报告该父仓库边界；未明确授权使用该父仓库或在项目内独立建仓时，不提交父仓库，也不嵌套 init。边界明确后，用 `git branch --show-current`、`git status --short`、`git diff`、`git diff --cached` 核对分支、工作区和**已有暂存内容**；新文件也要检查内容。不要把未提交修改当成切换分支时会自动消失的东西。
2. 先列明本次提交的确切路径；下面的范围与敏感内容检查全部通过后，才使用 `git add -- <本次确认的路径>`，不使用全量 add 或宽泛目录收录无关文件。add 后再次核对暂存差异与提交范围，才执行 commit。
3. **已有无关暂存不能混入本次 commit**。保留其内容和暂存状态，不自行 reset、restore --staged 或清空暂存区。提交范围已明确时，可直接采用能够验证保留无关内容与暂存状态的隔离方式，无需用户再次批准技术实现；执行前后核对相关差异。无法保证隔离时，停止本次提交并说明范围冲突，待用户决定如何处理后继续。
4. 不收录真实密钥、运行数据或依赖：检查 `.env`、`.env.*` 及其他可能含凭据的文件，`storage/`、`Storage/`、`node_modules/`、虚拟环境、`__pycache__/` 和运行时音频。**确认只含空值或安全占位符的 `.env.example` 可以提交。**先核对 `.gitignore`，只读检查不能靠文件名替代内容检查。
5. 已跟踪或已暂存的敏感文件不会因新加 `.gitignore` 自动安全；发现时停止提交并报告文件路径，不输出密钥、不擅自改写历史。缺少忽略规则时提出具体修正，获得该文件修改授权后处理。
6. 没有待提交变化就报告已有版本，不制造空提交。commit 说明写明功能和验证范围；中途存档可标注“未完成／待测”，不冒充验收结果。

## 远端、推送与 PR

- 检查实际配置的 remote、目标分支和将推送的提交范围；远端名字不一定是 `origin`。用户只授权 push 时，未提交文件留在本地，不顺手收录。
- 没有 remote 或真实地址时报告缺项；不猜仓库地址、不替用户创建 GitHub 仓库。已有 remote 与用户提供地址不一致时先说明，不擅自覆盖。
- 首次连接或首次推送前，检查远端是否已有分支与历史。已有历史先检查双方关系和目标；不自动 pull、合并无关历史或以本地历史覆盖远端。
- 确认目标后，首次推送可用 `git push -u <远端> <分支>`，后续仍核对 upstream；回报实际提交编号和远端分支，不把本地存档说成已上传。
- “推送 PR”只处理已有提交；未提交修改保留在本地并报告，不顺手存档。核对真实 GitHub 仓库和 head/base，检查相同来源仓库、源分支、目标分支是否已有 PR；有打开的 PR 就复用并回报链接，不重复创建。已关闭或已合并的 PR 先报告状态，不擅自重开或重复创建。
- 没有对应 PR 时，根据实际差异和已提供的测试事实创建 PR，标题与说明写清本轮内容和未验证项。使用可用的 GitHub 工具或 CLI 执行；创建 PR 的授权不包含点击合并、批准 PR 或开启自动合并。
- 若用户说的是“后续接口开发完成后推送 PR”，这是后续阶段安排，不在创建分支时提前推送或创建 PR；到达约定阶段后沿用该授权，不反复索要同一许可。

## 合并与失败处理

- 合并必须有明确源、目标、用户认可的测试事实和 merge 授权。合并前核对分支、差异与未提交工作；先保留用户工作，不盲目切换或清理。
- 用户授权本地 merge 时，合并后报告结果与主线复测项目；**等待用户复测主线通过，再执行已获授权的主线 push**。复测未通过时不推主线。
- PR 创建与 PR 合并是不同动作；PR 合并会直接改变远端，需要明确的合并授权和验收安排，不能从“推送 PR”推断。若用户已经通过 PR 合并，检查实际状态，按授权同步本地并据实回报，不重复 merge。
- 任何一步失败立即停下，报告成功步骤、当前分支／提交编号、未完成动作及错误。commit 成功但 push 失败时保留现有 commit，不重做存档；push 被拒绝时先检查，不自动 rebase、强推或重写历史。
- 不自行执行丢弃修改、改写历史、删除分支等超出上述动作的操作；这些需要单独明确范围与授权。

## 课堂例子

语音项目：03 骨架测试通过后，让 AI：“打存档点：骨架构建”，在 main 首次存档；04 在开发该接口前，让 AI：“创建feat/voice-metting分支，后续接口会在该分支上开发”。后续沿用这个功能分支：05—09 仅做后端接口独立测试，通过后用“打存档点：本轮名称”保存阶段版本，不逐个接入前端；09 全部后端接口独测通过并存档后，推送该分支并创建到 main 的后端阶段 PR，注明“后端独测通过，前端待联调”，不称全链路通过；10 继续在同一分支统一接入前端，联调通过后存档；11 完整验收后存档、推送同一分支并更新已有 PR 的内容与测试结果，不重新创建 PR，不自动合并或推送 main。
